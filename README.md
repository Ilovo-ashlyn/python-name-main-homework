# Homework：`if __name__ == '__main__':` 的含义，why？

> Python 作业 · 纯标准库、零依赖 · Python 3.8+

## 一句话回答

这行代码在问：**「当前这个 `.py` 文件，是被当成程序直接运行，还是被别的模块 `import` 进来的？」**
只有「直接运行」时，它下面缩进的代码块才会执行。

## 1. 含义：把这四个部分拆开看

| 片段 | 含义 |
| --- | --- |
| `__name__` | 解释器在加载**每一个**模块时自动创建的字符串变量，表示「这个模块叫什么名字」 |
| `'__main__'` | 解释器给**程序入口文件**起的特殊名字（`__main__` 模块） |
| `==` | 值比较，判断 `__name__` 当前是不是这个特殊字符串 |
| `if ...:` | 条件成立，才执行下面缩进的代码块 |

核心机制：`__name__` 不是关键字，也不是我们自己定义的，它由解释器按**加载方式**自动赋值：

- `python demo_module.py` → 该文件的 `__name__` = `'__main__'`
- `import demo_module` → 该文件的 `__name__` = `'demo_module'`（在包里则是 `pkg.demo_module`）

所以同一份代码，两种启动方式会有两个不同的 `__name__`，这行 `if` 就是一个「运行方式开关」。

## 2. 为什么需要它（why）

### ① 让一个文件同时具备两种身份
写模块时，我们既希望别人能 `import` 它复用函数/类，又希望自己能直接运行它做演示、自测或当命令行工具。没有这道判断，二者只能选一个。

### ② 避免「导入副作用」
Python 的 `import` 会**从上到下执行**被导入文件的所有顶层代码。如果测试代码、打印、连数据库、写文件、启动服务等写在顶层，别人只是想用你一个函数，也会被迫触发这些动作。保护块把这些「只在主动运行时才该做的事」关起来。

本项目里 `no_guard.py`（无保护）与 `import_no_guard.py` 就是反例演示。

### ③ 明确程序入口，项目更好组织
入口逻辑收进 `main()`，文件结构变成「定义 → 判断 → 调用」：

```python
def main():          # 1. 定义：函数、类、常量
    ...

if __name__ == '__main__':   # 2. 判断：我是入口吗？
    main()                   # 3. 调用：是，才启动
```

### ④ 防止多进程递归创建子进程（进阶但很典型）
Windows / macOS 上 `multiprocessing` 默认用 `spawn` 启动：子进程会重新导入主模块。若创建子进程的代码没有放在保护块里，子进程导入时又会创建子进程，导致无限递归或直接报错。官方文档因此要求把进程启动代码放在 `if __name__ == '__main__':` 里。

### ⑤ 没有它会怎样？
不是「程序跑不起来」，而是：**代码被复用时行为失控**——多打印、多执行、耗时、报错。这也是为什么它是 Python 工程惯例，而不是语法要求。

## 4. 常见误区

- 用 `==` 比较字符串，不要写 `is '__main__'`；也不是 `=`。
- 是双下划线 `__main__`，不是 `main`、`__main` 或 `__name__`。
- Python **没有**像 C/Java 那样强制的 `main` 入口；`main()` 只是约定俗成的函数名，真正起作用的是这个 `if`。
- 保护块只保护缩进内的代码；`import`、全局变量、类定义、顶层 `print` 在导入时依然执行。
- 被导入时 `__name__` 是模块名，不是文件路径，也不是 `'__main__'`。
- 包目录下的 `__main__.py` 是另一层机制：`python -m 包名` 会去执行它，和本题的写法配合使用。

## 6. 结论

`if __name__ == '__main__':` 不是语法规定，而是一种**模块边界约定**：把「被别人导入时该提供的能力」和「自己作为程序运行时该做的事」分开。它让代码可复用、无意外副作用、入口清晰，因此几乎出现在所有正经的 Python 脚本里。
